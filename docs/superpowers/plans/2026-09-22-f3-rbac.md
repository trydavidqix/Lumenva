# F3 RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fechar o enforcement server-side de RBAC no produto usando somente `viewer < agent < manager < admin` por organização e `platform_admins` como única exceção cross-tenant, com testes que provem negação antes do side effect.

**Architecture:** Manter `user_organizations.role` como fonte canônica dos quatro papéis humanos e `platform_admins` como fonte canônica do papel cross-tenant. Centralizar decisões em helpers de autorização server-side; RLS continua defesa em profundidade e `createAdminClient()` nunca substitui o gate de negócio. `ai_operator` permanece um ator interno de automação, fora de `user_organizations`, e não será introduzido no CHECK de roles humanos.

**Tech Stack:** Next.js route handlers/server actions, TypeScript, Supabase Auth `getUser()`, Postgres RLS/SECURITY DEFINER, Vitest, invariants/test-db, `pnpm typecheck`.

**Spec:** `docs/specs/01-spec-platform-base.md` §5; `docs/specs/13-spec-governanca-atendimento.md` §4; `.claude/rules/security.md` §RBAC/MFA/platform admin; `.claude/rules/multi-tenancy.md` §Platform admin/Auth e RBAC.

## Global Constraints

- Roles tenant canônicas: `viewer < agent < manager < admin`.
- `platform_admins` é a autoridade; não criar/usar coluna normativa `auth.users.is_platform_admin`.
- Toda autorização server-side usa `getUser()`, membership ativo e organização confiável.
- UI escondida não conta como enforcement.
- Service role exige filtro explícito de `organization_id`, preserva RBAC/ownership e audita mutações relevantes.
- Toda mudança de schema/RLS/ACL sai em migration versionada + apêndice idempotente em `supabase/baseline.sql` + linha em `supabase/migrations/MANIFEST.md`.
- Platform admin só atravessa tenant por caminho explícito, auditado com acting-as/bypass; alterações em `platform_admins` continuam DBA-only.
- Não alterar F1/F2 como fonte de identidade/tenant; `user_organizations` continua a membership efetiva.

## Review Focus

1. Viewer/agent não podem executar mutações de integração, mídia, settings, tokens ou equipe antes de qualquer upload/insert/side effect; cobrir rotas/actions com mocks que falham se o client externo for chamado.
2. Agent não pode escrever config de pipeline/settings nem ler/escrever recurso de outro agente fora do escopo definido; cobrir `own_and_unassigned` e `manager+`.
3. Manager pode operar o que a matriz permite, mas não pode alterar role, tokens, settings gerais ou billing; cobrir positivo e negativo.
4. Platform admin passa somente por `platform_admins` ativo + MFA quando exigido, com audit explícito; um DTO/cookie/flag fabricado não basta.
5. Membership revogada, role desconhecida, ausência de org e erro de RPC falham fechado; resposta não expõe mensagem de banco.

## Auditoria atual — estado antes do F3

- **Base correta:** `apps/crm/lib/auth/require-role.ts` já resolve usuário via `loadAuthUser`, org ativa, `fn_user_role_in_org`, rank e `forbidden_role`; `allowPlatformAdmin` é opt-in. `apps/crm/lib/auth/requirePlatformAdmin.ts` consulta `platform_admins`, `revoked_at` e MFA AAL2, mas é redirect-oriented e não serve diretamente como guard JSON de API.
- **Cobertura existente:** `apps/crm/tests/unit/rbac-matrix.test.ts`, `apps/crm/tests/invariants/gov-1-rbac.test.ts`, `apps/crm/tests/invariants/gov-1-rbac-config-write.test.ts` e `apps/crm/tests/e2e/rbac-roles.spec.ts` cobrem a matriz central, porém não inventariam todas as rotas nem todos os Server Actions.
- **Gaps confirmados por leitura:** `conversations/[id]/media` aceita sessão + org e usa admin storage sem `requireRole`; `onboarding/whatsapp/session` aceita sessão + org e permite POST que cria/reativa sessão sem gate de admin; `system/version` e `system/update` usam `user.is_platform_admin` diretamente e o POST não exige MFA AAL2; `channels/templates` e `channels/official` duplicam `ROLE_RANK` localmente; `contacts/_handler.ts`, `message-templates`, notas de conversa e alguns actions também duplicam rank/role fora do helper único.
- **Gaps de consistência:** `apps/crm/lib/auth/types.ts` inclui `ai_operator` no tipo/rank, embora o banco aceite apenas quatro roles humanos; isso é um ator interno intencional, mas precisa ficar tipado/separado para não virar caminho de membership ou role de rota.
- **SQL já parcialmente endurecido:** `fn_is_platform_admin`, `fn_user_org_ids`, `fn_user_role_in_org` e `fn_role_at_least` têm revoke/re-grant em migration `0108`; a varredura genérica `hardening-definer-varredura.test.ts` vigia funções SECURITY DEFINER. A ACL do objeto `platform_admins` ainda aparece ampla no dump (`GRANT ALL` para `anon`/`authenticated`) e deve ser medida no Postgres real antes de decidir forward-fix; RLS atualmente é a barreira efetiva.
- **Fora do F3:** `/readyz`, webhooks assinados, cron com segredo interno e MCP Bearer têm autenticação própria; serão classificados e testados como boundaries não-humanos, não receberão `requireRole` artificial.

## Critério de conclusão

F3 só fica pronto quando todos os gates server-side classificados como tenant-aware têm guard explícito ou autenticação não-humana documentada, a matriz de 4 roles e platform admin passa no Postgres real, nenhuma migration/ACL foi alterada fora da tripla, typecheck/unit/invariants/test:db ficam verdes, e a revisão independente não encontra bypass ou vazamento de existência.
